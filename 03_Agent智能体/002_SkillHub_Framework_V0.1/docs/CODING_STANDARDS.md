# SkillHub Framework Coding Standards

状态：强制执行

本规范是 Codex、开发人员和代码审查者必须遵守的工程标准。它补充 `ARCHITECTURE.md` 与 `CODING_RULES.md`，不得用于绕过 Constitution 的职责边界。

## 1. Python 环境

- 目标运行环境统一为 Python 3.11；
- 第三方库只使用稳定正式版，并锁定兼容版本范围；
- 禁止使用废弃 API、预览接口或停止维护的依赖；
- 引入依赖前必须评估许可证、安全、维护状态和替代方案；
- 代码必须在声明的 Python 3.11 环境中通过测试。

## 2. 数据契约

所有公开模块、Service、Skill、Tool、MCP 接口和跨层调用必须明确：

- Input Schema；
- Output Schema；
- 必填与可选字段；
- 字段类型、默认值、约束和错误语义；
- Schema 版本与兼容策略。

未经契约评审，禁止：

- 私自增加字段；
- 删除字段；
- 修改字段类型；
- 改变字段含义或空值语义；
- 返回文档未声明的临时结构。

无法按契约实现时，必须在交付前明确说明限制、影响范围和替代方案，不得伪造完整支持。

## 3. 工程质量

所有文件 I/O、网络请求、MCP 调用和 LLM 调用必须具备：

- 明确的异常捕获与错误分类；
- 可配置的超时控制；
- 有限重试：次数可配置、过程可观测，且仅用于可安全重试的场景；
- 文件、连接、会话、流和临时资源的可靠释放；
- 失败后的状态一致性、必要回滚和审计记录。

禁止无限重试、无超时阻塞、吞掉异常或在失败后返回伪成功结果。

## 4. 模块设计

- 禁止滥用全局变量和可变单例；
- 模块保持高内聚、低耦合和单一职责；
- 外部依赖通过接口与依赖注入提供；
- 业务逻辑与文件、网络、框架实现分离；
- 组件必须支持单元测试、Mock 和替代实现；
- 启动装配集中在 Composition Root，不在业务模块中创建基础设施。

## 5. 日志规范

日志至少分为：

- `INFO`：生命周期、路由、调用完成和可预期业务状态；
- `ERROR`：任务失败、依赖故障、契约错误和无法恢复的异常。

结构化日志必须按上下文支持以下字段：

- `trace_id`；
- `task_id`；
- `doc_id`；
- `page`；
- `skill_name`。

不适用字段可为空，但字段名称不得自行变更。日志禁止记录 API Key、令牌、密码、完整敏感文档或未经脱敏的个人信息。

## 6. 大批量任务

文件批处理和长耗时任务必须预留异步扩展接口，包括任务提交、状态查询、取消、超时、幂等和失败重试边界。

禁止把长时间阻塞同步调用固化为唯一执行模式。V0.2 可以使用本地同步实现，但接口设计必须允许未来替换为队列或异步执行器。

## 7. 文档处理规范

涉及 Word、Excel、PDF、CAD 和文本切片时，必须：

- 将页码范围、Sheet、编码、切片大小、重叠范围、渲染参数等配置化；
- 支持调用方在安全范围内自定义参数；
- 保护原文件、格式、公式、样式和元数据；
- 保留 `source metadata`，至少可追踪源文件、文档 ID、页码/Sheet、位置和处理版本；
- 对不支持的格式、损坏文件和精度限制明确报错。

## 8. 配置规范

禁止在代码中硬编码：

- API Key、Token、密码和其他秘密；
- 本机绝对路径或环境相关目录；
- 超时、重试、模型、批量大小等运行参数。

配置统一由 `config` 与 environment 提供。秘密只通过环境变量或受控秘密管理系统注入；配置必须支持类型校验、默认值说明和环境覆盖。

## 9. 输出规范

执行开发任务时，应先说明实现思路、职责边界和影响范围，再提供完整、可运行、可测试的实现。

禁止：

- 输出残缺代码、伪代码或缺少关键模块的片段作为完成结果；
- 用 Demo 代替明确要求的正式实现；
- 隐瞒未实现能力、测试失败或环境限制；
- 只展示代码而不说明运行与验证方法。

当任务明确限定为骨架或 Demo 时，必须标注其适用范围和非生产限制。

## 10. SkillHub 架构约束

### Agent

只负责理解、拆解和调度，不写业务逻辑，不直接访问 Knowledge、Tools、MCP 或文件。

### Skill

执行业务流程，不调用其他 Skill，不直接调用 MCP、Knowledge Router 或 Tool；基础设施能力必须通过 Service Layer。

### Service

负责协议适配、数据转换和基础设施调用，不包含业务判断，不选择 Skill，不实现 Agent 行为。

### MCP Server

只暴露外部能力和资源，不包含业务逻辑、任务拆解或 Skill 路由。

任何跨层快捷调用都视为架构违规，即使功能可以运行也不得合并。

## 11. 演进兼容

代码设计需要为以下演进保留稳定契约和可替换接口：

- MD → RAG：Knowledge Router 上层查询契约保持稳定；
- Local Queue → Redis：任务接口与队列实现解耦；
- Single Agent → Multi Agent：上下文、Runtime、路由和审计接口不绑定单一实现。

“支持演进”不等于当前启用目标架构。Multi Agent 等破坏冻结基线的变化，必须先更新 Constitution、完成版本评审和迁移设计，不得在普通功能开发中隐式引入。

## 12. 审计与验收

每项开发必须能说明：使用的数据契约、依赖版本、配置来源、异常与重试行为、日志字段、测试结果和已知限制。提交前执行测试、静态检查、格式检查和暂存范围检查，确保运行产物和秘密不进入提交。
